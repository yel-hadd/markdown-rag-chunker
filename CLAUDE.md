# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An open-source Apify Actor ("Markdown RAG Chunker", Store slug `codepoetry/markdown-rag-chunker`) written in Python 3.13. It converts documents to Markdown with `markitdown`, splits them with LangChain text splitters, and pushes one dataset item per chunk. `README.md` is the public Store listing — it is user-facing marketing copy, so keep its claims accurate and in sync with actual behavior. Follow TDD: write the failing test first for any behavior in `src/models.py` or `src/processing.py`, keep code and comments minimal and high-quality.

## Commands

```bash

apify run                                            # run locally; input from storage/key_value_stores/default/INPUT.json
python -m src                                        # same entry point as .actor/Dockerfile's CMD
apify push                                           # build and deploy to Apify (authenticated as codepoetry)
apify call 84h4GucI0gbo1SrN7 -i '<json input>' -o   # verify a deployed build end to end
```

Run the tests from the repo root, because they import `src.*` as a package. `src/main.py` cannot be unit-tested locally (it imports `apify`), which is why all logic lives in `processing.py`/`models.py` and network wiring is verified with real `apify call` runs after each push.

## Architecture

- `src/main.py` — the Actor runtime and the only module touching Apify or the network. It parses input into `MarkdownSplitterInput`, resolves the fetch proxy (user's own `proxy_url` wins, else `use_apify_proxy` via `Actor.create_proxy_configuration`, only in file mode), then defines the I/O closures: `fetch_remote` (curl_cffi `AsyncSession` with `impersonate="chrome"`, a 30s timeout and `stream=True` — a real Chrome TLS/HTTP2 fingerprint; plain HTTP clients get 403'd by sites like Wikipedia; the body is read through `read_capped` with a 25 MB limit on the decompressed size, plus a `Content-Length` fast fail) and `load_kvs` (reads `kvs://KEY` from the store chosen in the `kvs_store` resource picker — the only way a limited-permission run may read a user's store; plain text only, not run through markitdown). For `http(s)` sources it downloads once up front (reusing the payload for conversion), applies change detection, splits via `processing.split_documents`, pushes one dataset item per chunk, then writes run metrics to the `OUTPUT` record (on failure OUTPUT is `{failed: true, error}`; errors are flattened with `validation_error_message`/`http_error_message`). Downloads retry transport errors, 429 and 5xx up to twice (`retry_delay`, ≤5 s waits, non-finite `Retry-After` ignored) with a 90 s timeout. If the user's maximum charge per run truncates the push (`ChargeResult.event_charge_limit_reached` with `charged_count < len(chunks)`), OUTPUT reports the delivered count with `charge_limit_reached: true` and the cache is not written. Any exception goes to `Actor.fail`.
- `src/processing.py` — pure logic, testable without Apify. `resolve_markdown_text` takes injected `fetch_remote`, `load_kvs`, `convert_remote_file` callables (sync or async; `_maybe_await`). `convert_to_markdown` passes markitdown a `StreamInfo` (MIME type and charset split from Content-Type, URL, extension; `application/octet-stream` treated as unknown) — markitdown 0.1.x silently ignores a `mimetype=` kwarg, so never pass hints any other way. `split_documents` maps header levels to `Header N` metadata keys, drops sections with empty content (they would become billed zero-char chunks), measures sections in tiktoken tokens (`max_chunk_tokens`, default 512, `tokenizer` cl100k_base/o200k_base) or characters when `max_chunk_chars` is set (it overrides), fails early when the lower bound `sum(ceil(size/cap))` already exceeds `max_chunks` (avoids building huge document lists), re-splits **only** oversized sections (overlap = 10% of the cap; regex separators with zero-width sentence-end lookbehinds incl. CJK, spaces kept at piece start so summed piece tokens match real counts; any piece that still overshoots is re-split, so no chunk exceeds the cap), and enforces `max_chunks`. `format_chunks` computes `chunk_id` (first 16 hex chars of sha256 over sorted-key JSON of scope + content + metadata, where scope is `document_source(params)` — `source_id`, the URL, or `kvs://<store>/<key>` — or `text:<document_hash>` for pasted text without `source_id`, plus an `occurrence` number for repeats within a document), exact `token_count` with tiktoken, and the provenance fields `header_path`, `embedding_text` (header path + blank line + content), `chunk_index`, `chunk_total`, `source`, `document_hash`. `document_hash` fingerprints the converted document, `source_fingerprint` the raw download (bytes + content type), `cache_record_key` names a source's cache record, `cache_hit` decides whether a cached state matches, and `split_config_fingerprint` hashes every input that affects splitting (headers, strip_headers, max_chunk_chars, max_chunk_tokens, tokenizer) so the change-detection cache never reports a stale hit. Tests inject fakes instead of mocking network calls; the markitdown fake is strict (keyword-only `stream_info`) and two tests run the real markitdown.
- Change detection (`skip_if_unchanged`): one named KVS per user (`markdown-rag-chunker-cache`) holds a record per source (`state-<sha>` of `[cache_namespace, document_source or hash:<document_hash>]`) with `{document_hash, source_hash, split_config, chunk_count, input_chars, input_file_type}`. File mode checks `source_hash` before conversion (an unchanged download skips markitdown entirely), then everything falls back to `document_hash` after conversion (dynamic pages whose bytes vary per fetch). On a hit the run pushes nothing and exits with `unchanged: true` in OUTPUT. The store is created inside the run, so it belongs to the run's user — never the creator. Cache read/write failures are logged and ignored, never fatal.
- `src/models.py` — Pydantic models holding all validation (`hide_input_in_errors=True`, so proxy credentials and huge texts never reach logs): `input_mode` is inferred from whichever of `markdown_text`/`markdown_file` is set (both set without a mode is an error, never a guess), `max_input_chars` (checked in text mode at validation, in file mode after conversion), `max_chunk_tokens` (default 512, 50–8192, `null` disables), `max_chunk_chars` (optional override, min 100), `headers_to_split_on` (default `#`/`##`/`###`), `max_input_chars` (default 2,000,000), `cache_namespace`, header format (1–6 `#` characters, entries normalised so `' ## '` and `'##'` fingerprint identically), `proxy_url` (blank means none; case-insensitive `http://`/`https://`/`socks5://`; only the scheme is lowercased; errors never echo the value), proxy mutual exclusion, and `kvs://` requiring `kvs_store`. `MarkdownChunk` shapes dataset items; `ProcessingMetrics` shapes the `OUTPUT` record.
- `.actor/Dockerfile` — the build image (`actor.json`'s `dockerfile` path is relative to `.actor/`): `apify/actor-python:3.13`, tiktoken encodings baked in at build time (`TIKTOKEN_CACHE_DIR=/opt/tiktoken`, so runs never download them), non-root user, CMD `python3 -m src`. There is no root Dockerfile. `.dockerignore` keeps `.git`, local `storage/`, tests and docs out of the image.

## Keep these in sync

- Input fields: `src/models.py` ↔ `.actor/INPUT_SCHEMA.json` (pinned by `SchemaCongruenceTests`). The platform applies schema `default`s to API runs, so source fields (`input_mode`, `markdown_text`, `markdown_file`) must only use `prefill` — a default URL once made API calls with only `markdown_text` chunk and bill Wikipedia instead. Apify's daily Store test runs the prefill input and needs a non-empty dataset, so `markdown_file`'s prefill must stay a working URL we control (this repo's README on raw.githubusercontent.com): Wikipedia returned HTTP 429 to Apify IPs after a day of test runs. Model `Optional` fields need `"nullable": true` in the schema.
- Output shape: `src/models.py` (`MarkdownChunk` per dataset item, `ProcessingMetrics` for the `OUTPUT` record) ↔ `.actor/dataset_schema.json` (one chunk per item) ↔ `.actor/output_schema.json` (templated links only — every property needs a `template`, e.g. `{{links.apiDefaultDatasetUrl}}/items`; the platform rejects anything else at build time) ↔ the README output table.
- Limits and memory: `.actor/actor.json` and the `max_*` defaults ↔ `docs/pricing-and-hardening.md`.
- Feature claims: README ↔ actual behavior. No misleading claims — pricing examples, proxy billing, and format support must match the code.

## Billing

Pay-per-event with only Apify's synthetic events: `apify-actor-start` and `apify-default-dataset-item`. The code never calls `Actor.charge()`; `docs/pricing-and-hardening.md` says never to add custom events or charge event names starting with `apify-`. Published prices: `apify-actor-start` $0.001 (all tiers) and `apify-default-dataset-item` $0.0008/$0.0007/$0.0006 per chunk, i.e. $0.80/1k chunks + $0.001/run. The creator pays **all** platform usage of users' runs (compute, storage, Apify Proxy) out of the 80% revenue share, so the start fee exists to make zero-chunk runs (skip hits, failed inputs) profitable; measured costs and the margin check live in `docs/pricing-and-hardening.md`. Revenue is the number of `Actor.push_data()` items (one per chunk) plus one start event per run. The `OUTPUT` record is written via `Actor.set_value` and is **not** billed. Changing how data is pushed, adding run time, or adding storage writes changes margins.

## Gotchas learned the hard way

- The input schema rejects `group`/`groupDescription`; use `sectionCaption`/`sectionDescription` to group fields.

- The platform validates `.actor/output_schema.json` at build time: every property must have a `template` (link-style outputs only).
- In crawlee ≥1.x, `ProxyConfiguration.new_url()` is async — `await` it.
- Pinning an old `apify` SDK broke every CLI-started run (`meta.origin: 'CLI'` not in its pydantic enum); keep `apify` reasonably current.
